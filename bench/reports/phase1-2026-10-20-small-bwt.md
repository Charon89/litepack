## One failed combination, not reproduced

`lpk/balanced/office-pdf` failed in its first repeat: the extracted tree differed from the corpus in two files (first: `arxiv-cc-by-small/arxiv-2505.06364v1.pdf`), so the runner recorded the combination as failed and the table above has no row for it. That class writes no `bwt` block (the stage tries no candidate there), and `lpk/balanced-no-bwt/office-pdf` in the same run verified. Afterwards, on the same idle machine and build: three archives written with the runner's command were byte-identical (and equal in length to the `balanced-no-bwt` row), six direct extractions of them verified bit-exactly, and the runner again on that class, three forced repeats per setting (`bench/results/2026-10-20-megatron-3`), verified every file of every repeat. The cause is not found; it points at the extraction side (the archive's bytes do not vary), not at the BWT stage. E2-22's run of `lpk` on `full` (started after these checks) verifies every file of every repeat and would record a recurrence.

## 8. Caveats

- tools skipped: none
- combinations that failed: lpk/balanced on office-pdf
- rows resting on one measurement (D-20 item 3): lpk/balanced-no-bwt on office-pdf (the first repeat's compress plus extract wall time reached --long-run-s (120 s): not repeated)
- probes not available: jpeg, deflate, dedup, text, weights, entropy-gate
- classes without an estimate rule (the best measured incumbent is used, no gain claimed): audio, source-git, vm-image
- antivirus: the scanner state changed during the run; scanner state at the start of the baseline run: Windows Defender (scanner off, state 0x60100); Avast Antivirus (scanner on, state 0x41000); at the end: Windows Defender (scanner off, state 0x60100); Avast Antivirus (scanner snoozed, state 0x42000)
- unclean inputs (dirty, unknown or unoptimised builds, no settle pause, directories outside bench/results): none
- the baseline's build profile is not recorded in its host file, so whether it was a release build cannot be checked from the result files
- the `small-files` text estimate compresses a tar stream of the class, so tar header bytes are included in it; the baseline sizes are of each tool's own archive
- probe text timing: `in-process` rows time a library call on a stream in memory, `process-wall` rows time a whole external program including start-up and file I/O; the two bases are not comparable, and the estimates here use sizes only
- estimates are derived from component measurements on one corpus; they are not archives that were written and read back
