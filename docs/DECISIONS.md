# Decisions (append-only; never edit a past entry — supersede it with a new one)

Format: `D-NN — YYYY-MM-DD — decision — reason`

- D-01 — 2026-10-01 — **Open-core.** Engine, CLI and `.lpk` format spec are open source (Apache-2.0 OR MIT) in a public repo; GUI Pro/enterprise features may be closed. — Dissolves the LGPL dependency question (preflate-rs → cabac, packMP3), answers "why trust a new format", and unlocks free CI/fuzzing/attestations for public repos.
- D-02 — 2026-10-01 — **Rust core on MSVC x64 + ARM64; Tauri 2 GUI; windows-rs shell extension.** — Memory safety is the security pitch; the key libraries (preflate-rs, lepton_jpeg, blake3, zstd, reed-solomon-simd, RustCrypto) are Rust; Tauri reuses the founder's web skills; both Windows targets are Rust Tier 1.
- D-03 — 2026-10-01 — **No executable decoder inside archives (no embedded WASM).** The format uses a versioned primitive set + published spec + reference decoder. WASM is only an app-side plugin sandbox. — SmartScreen/AV reputation, second sandbox to audit, non-deterministic relaxed-SIMD, conflicts with a small auditable reader.
- D-04 — 2026-10-01 — **No neural/transformer tier in the product; research track only.** — Today ~10 KB/s per core; NPU int8 is not bit-exact across vendors; Google patent US 12,154,304 (integer neural networks for entropy coding) requires FTO/licensing before any product use.
- D-05 — 2026-10-01 — **Balanced tier = LZMA-class/zstd-ultra + filters + Peel + Fold; BWT only on text-classified streams.** — BWT equals LZMA in size on mixed/binary data and decodes 4–5× slower; its 15–17% advantage is text-only.
- D-06 — 2026-10-01 — **Crypto: AES-256-GCM default, XChaCha20-Poly1305 optional; Argon2id; derived per-chunk nonces under a wrapped archive key; encrypted names optional (listable mode available).** — FIPS-validatable default for enterprise buyers; users expect "list without password".
- D-07 — 2026-10-01 — **Phase 0 gates (GO requires all):** on photo/document classes Balanced ≥ 10% smaller than WinZip Zipx and PowerArchiver `.pa` (where measurable; otherwise ≥ 10% smaller than the best measured incumbent on JPEG and Office/PDF classes) and ≥ 15% smaller than 7-Zip Ultra; ≥ 2× smaller on the versioned-backup class; video class stored at ≥ 80% of raw disk read speed; extraction (Fast tier) no slower than 7-Zip. — Numbers below these mean the product has no defensible edge; stop or pivot to a backup tool.
- D-08 — 2026-10-04 — **Phase 0 verdict: GO, with gates G2 and G3 of D-07 amended by D-27 (owner's decision, option B of two).** Measured on the `full` profile (`bench/reports/phase0-2026-10-03.md`; baseline `bench/results/2026-10-03-megatron-4`, probes `-megatron-5`, build `78bc960`; every figure recomputed from the JSON by a read-only review, `docs/notes/phase0-verdict-review.md`): G1 PASS — on `photo-jpeg`, `photo-jpeg-edited` and `office-pdf` combined the Balanced estimate is 83.6% of the best measured incumbent (zpaqfranz `-m5`; D-07's fallback wording, WinZip and PowerArchiver not measured) and 81.0% of 7-Zip Ultra (photo-jpeg alone 82.4% / 79.8%, edited 82.4% / 78.5%, office-pdf alone 91.0% / 89.1% — the photo classes carry the pass; the JPEG probe recompressed 3,640 of 3,655 files 22.2% smaller with 0.41% stored as-is); G4 PASS — zstd level 3 extracts the three mixes at 333.7, 130.6 and 1152.8 MB/s against 218.6, 82.1 and 502.3 MB/s for 7-Zip `-mx5`; G2 FAIL as written — the estimate is 110.2% of zpaqfranz `-m5` and 99.4% of 7-Zip Ultra on `backup-versions`, because the whole 25.5 MB class fits inside a solid incumbent's dictionary and every solid setting already removes the cross-version redundancy (2× against them would need version 1 alone at 10% of its bytes; the estimate is 7.3% of the raw bytes and 24.3% of rar non-solid); G3 FAIL as written — the `store` control writes `video` at 32.1% of the uncached raw read (4663.4 MB/s), a bound every archiver shares because the proxy reads and writes on one disk. — G1 and G4 are the product's pitch and passed with margin; G2 and G3 failed on their definitions, not on the method, so the verdict is GO and the two gates are restated in D-27 as Phase 1 gates to be measured with real LitePack output.
- D-09 — 2026-10-01 — **Peel is fallback-first:** every inversion verified by re-encoding at compress time; net-gain gate on the full stream; failures stored as-is and counted. — Lepton rejected 3.6% of files at Dropbox; ~1% of in-the-wild JPEGs fail JPEG XL reconstruction; preflate overhead is unbounded for unrecognised encoders.
- D-10 — 2026-10-01 — **Priors (dictionaries, later models) are bundled with the app release and referenced by ID; no network required to decode.** — SDCH died of the fetch dependency; archives must open offline in 2036.
- D-11 — 2026-10-01 — **Recovery records use Reed-Solomon (reed-solomon-simd); RaptorQ excluded.** — RaptorQ's patent covenant covers only full RFC 6330 implementations and a patent runs to ~2030.
- D-12 — 2026-10-01 — **Fold orders files (not chunks) by similarity; chunk-level dedup only.** — Chunk reordering turns extraction into random writes; nilsimsa ordering is O(n²) beyond a few hundred thousand items.
- D-13 — 2026-10-01 — **The project must be workable from any of the owner's computers; the GitHub repo is the only shared state.** A machine is prepared by `scripts/setup-windows.ps1`; `main` is pushed after every reviewed task; durable knowledge lives in the repo, not in per-machine tool memory; line endings are normalised to LF by `.gitattributes`. — The owner works on several computers; anything that exists on one machine only (installed tools, unpushed commits, local notes) blocks the others.
- D-14 — 2026-10-01 — **Corpus sources: GovDocs1 stays; DIV2K and CLIC 2021 are left out** (owner's call, deviating from `docs/CORPUS.md` for the second). GovDocs1's host warns its files "may contain malware"; the builder only stores and compresses them and records expected versus found file counts in `build-info.json` in case antivirus quarantines any. `photo-raw-png` is built from Kenney CC0 PNGs, the Kodak set and local PNG/BMP conversions of the CC0/CC-BY photos instead. — GovDocs1 is the only large public set of real Office/PDF files; DIV2K is "for academic research purpose only" and CLIC states no usage terms, while results measured on the corpus are committed to a public repo.

- D-16 — 2026-10-01 — **The corpus downloader uses `reqwest` (blocking) with `native-tls`, i.e. the operating system's trust store.** — `ureq`'s TLS features and the usual rustls setups pull `webpki-roots`/`webpki-root-certs`, which are CDLA-Permissive-2.0 and not on the `deny.toml` allow-list; the OS trust store needs no bundled root data.
- D-17 — 2026-10-01 — **Corpus sources, second round:** (1) Commons photos also accept CC BY-SA (owner's call; `docs/CORPUS.md` says CC0/CC-BY); (2) `backup-versions` `v1`–`v3` are exported from pinned git commits by the same kind that builds `source-git`, not downloaded as GitHub-generated tarballs; both classes need the `git` program and are skipped, visibly, without it; (3) the NYC taxi CSV is a server-generated export pinned as downloaded, so a mismatch means the generator changed and the source is re-pinned; (4) libultrahdr's sample JPEGs are CC-BY-4.0 per its `tests/data/LICENSE` (the spec says Apache-2.0); (5) arXiv papers come from the OAI set `cs:cs:CR`, because whole-archive listings time out; (6) a pinned Commons or arXiv file that later changes or disappears upstream stops the build with a message naming it; `--allow-unavailable` builds without such files and records them in `build-info.json`, so a corpus never shrinks silently. — CC0/CC BY alone cannot supply 300 small or 3,000 camera JPEGs from "Featured pictures", and the corpus is rebuilt by recipe and never redistributed, with licence and author recorded per file; GitHub has changed its archive packing before, while git objects are content-addressed; the rest was found while building and reviewing the `small` profile and keeps the build reproducible from the committed lock.
- D-18 — 2026-10-01 — **Derived corpus files come from in-tree, integer-only code where no allow-listed crate fits.** JPEGs re-encoded for `photo-jpeg` (from the Kodak set) and `photo-jpeg-edited` use a small in-tree encoder: baseline with the standard Annex K Huffman tables, progressive by spectral selection without successive approximation, edited photos keeping their source's EXIF/ICC segments. The built ZIPs use an in-tree ZIP writer; their Deflate streams, and the converted PNGs, come from the bundled static C zlib (which is therefore also the extraction backend) plus miniz. Golden BLAKE3 tests pin one output of every in-process derivation, so the Windows and Linux CI jobs fail on any byte difference. — The only pure-Rust JPEG encoder crate with progressive output, `jpeg-encoder`, carries the IJG licence, which is not on the `deny.toml` allow-list; real ZIPs contain genuine zlib streams, so the Deflate-recompression probe sees realistic input; integer-only code is the simplest way to get the same bytes on every machine.
- D-19 — 2026-10-02 — **How baseline tools are measured.** (1) Published peak memory is the peak resident set: on Windows the working-set peak of the tool's main process, on Linux `ru_maxrss`; the Job Object commit peaks that PLAN P0-3 names are recorded as separate Windows-only fields. (2) `bench/tools.toml` is the committed catalogue of tools and command lines; the versions actually used are recorded per results directory in `tools.json`, and machine-specific paths live only in the untracked `bench/tools.local.toml`. (3) WinRAR is measured with PLAN's settings in its default non-solid mode and additionally as `best-solid`; `best-rr3` carries `-md256m`, so it differs from `best` only by the recovery record. (4) Every setting runs at the machine's thread count, as a user would run it; tools whose ratio depends on the thread count are flagged in each result. (5) Directory-mode tools run in the parent of the class directory with relative paths, so no archive holds an absolute path; stream compressors (zstd, xz) are measured as the tar step plus the compressor step, each also recorded separately. (6) A results directory holds one run — `<date>-<host>`, with a numeric suffix for further runs on the same day — and results are written only from a clean, committed build unless a recorded flag says otherwise. — Committed and resident memory are different quantities and only the latter exists on both operating systems; one tracked file cannot hold each machine's tool versions (D-13); 7-Zip archives are solid by default, so a non-solid-only WinRAR would be handicapped; the rest keeps every published number reproducible from the result files.
- D-20 — 2026-10-02 — **Run-loop rules for the baseline measurements (amends D-19 item 5).** (1) Creation runs in the parent of the class directory with relative paths, as before; extraction runs in the combination's own scratch directory with plain relative names, for every tool. (2) A file handed from one step to the next (the archive, the intermediate tar) is flushed to disk outside the timed intervals, and a class's inputs are re-read before every tool × setting. (3) `--repeats` is an upper bound: a combination whose first repeat takes at least `--long-run-s` seconds of compress plus extract wall time (default 120) is measured once, and its result says so; PLAN P0-3's "median of repeats" is then that one value. (4) `run.json` is written last and lists every intended combination; a results directory without it, or disagreeing with it, does not validate. (5) WinRAR runs with `-cfg-`, zstd and xz without `-f`, and child processes get no tool-configuration environment variables. (6) Private corpora: result files never carry file names or tool output, and on Windows a class with non-ASCII paths is skipped for tar and the tar-stream tools, because the system tar cannot read such names from a list file. (7) The host file records the antivirus products that Windows Security Center reports, with their scanner state; extraction times include whatever real-time scanner is active. — From the review of the run loop: WinRAR's long-path handling fails when the output argument contains `/` or `..`; an unflushed archive is written out during the next timed step and penalises tools with large outputs; repeating a multi-minute combination adds hours and no information; an aborted run must not pass for a complete one; a `rar.ini` could silently change a setting.
- D-21 — 2026-10-02 — **The run loop pauses after deleting extracted files (adds to D-20).** After each repeat's verification the loop removes the extracted tree; before the next timed step it now waits 500 ms per 1,000 files removed (minimum 250 ms, maximum 30 s; `--settle-ms-per-1000-files`, recorded in `run.json`; `run --compare` refuses two runs that differ in it). — The first pair of acceptance runs (`bench/results/2026-10-02-megatron` and `2026-10-02-megatron-2`, measured without the pause) agreed within the 3% limit on every compress total but not on four extract totals. Their per-repeat values show two timing modes for the extraction of classes with thousands of files; the slow one occurs when the extraction starts within seconds of the previous repeat's files being deleted, which happens to fast tools (tar, zstd level 3) and not to tools with a long compress step. Those two result directories therefore overstate the extraction time of fast tools on many-file classes; they stay in the repository as the evidence for this decision and are not to be used for the report. Check of the remedy, same day, same build (`ffdb753`), `small-files` class (20,000 files) with tar and zstd, five repeats: without the pause (`bench/results/2026-10-02-megatron-3`) the extract times of tar and zstd level 3 are spread out and slower than those of zstd level 19 and ultra; with the pause (`2026-10-02-megatron-4`) all four settings sit in one tight group at the fast value. If a later run again shows two groups on many-file classes, the fallback is to extract each repeat into its own directory and delete them together at the end of the combination, not a longer pause. Open, low severity: `run.json` files written before the pause have no field for it and read as zero; raising the schema version for new runs would close the gap for hand-edited files.
- D-22 — 2026-10-02 — **How the component probes measure (P0-4).** (1) Probes run from release builds only; every probe file records the build profile, the library's thread setting and the version of each library it used, and `run --validate` checks probe files against their typed format, their table and the directory's host and build. (2) The named `deny.toml` exception for `cabac` (LGPL-3.0-or-later, required by `preflate-rs`) is in place, as D-01 and `docs/LICENSING.md` provide for. (3) The Deflate probe walks ZIP, PNG, gzip and PDF containers itself, one level deep, because the published `preflate-rs` 0.7.6 has no container scanner; "recognised versus unrecognised encoder" is not something the library reports, so streams are grouped by the library's encoder estimate and by correction overhead. (4) In-process compressors are measured with the libraries this crate links (libzstd 1.5.7 and liblzma 5.8.4 as the generic C build of `liblzma-sys`, without its SIMD and unaligned-access paths), single-threaded, with every allocation and codec set-up outside the timed interval; external tools are measured as whole processes and labelled so; speed comparisons across tools use the process rows. (5) `probe weights` compares byte planes and bit-rotated planes against plain zstd at the same level and window; the `small` profile has no safetensors file, so its numbers come from `full`. (6) `probe entropy-gate` also measures raw disk read speed with the cache bypassed, per class; the D-07 video gate uses the video class's own rate from the `full` profile. (7) Probe files never carry file or folder names of a private corpus; group labels are numbered in natural order. — Each point came out of the reviews of the framework and the six probes: debug builds would have written speed figures without saying so; the PLAN's wording assumed a container scanner the crate does not publish; the bundled xz build was found slower than upstream `xz`; the first weights comparison used different windows on the two sides; the first version deltas measured tar header names rather than content.
- D-23 — 2026-10-02 — **What the Phase 0 report computes (P0-5).** (1) `lpk-bench report --results <baseline directory> --probes <probe directory>… --mixes bench/report-mixes.toml` reads only validated result directories; inputs the decisions rule out — a baseline measured without the settle pause of D-21, a dirty or debug build, a directory outside `bench/results` — are refused unless `--allow-unclean` is given and are then marked in the title and the verdict line. (2) Every number in the report carries the index of the result file it came from; estimates are labelled as estimates and derived per class by fixed rules: the JPEG classes from `probe-jpeg` with failed files stored as-is; the Deflate-bearing classes from `probe-deflate` (peeled data plus corrections, xz preset 9); `backup-versions` from `probe-dedup` (the smaller of unique-chunk compression and version one plus patches); the text classes from the best verified `probe-text` row; `model-weights` from the better plane variant; `video` and `encrypted-random` stored; every other class the best measured incumbent with no gain claimed. (3) Three disk mixes with byte weights live in `bench/report-mixes.toml` (photo-doc, developer, video-heavy); the first weights are the orchestrator's assumptions and the report prints them. (4) "The best measured incumbent" of D-07 is the best single tool × setting over the combined bytes of the classes concerned; the sum of per-class bests is printed as a stricter second figure. (5) Gate proxies: G1, photo/document size, against that incumbent and 7-Zip Ultra on `photo-jpeg`, `photo-jpeg-edited` and `office-pdf` together (WinZip and PowerArchiver were not measured, so D-07's fallback wording applies); G2, `backup-versions`, against the best incumbent; G3, the baseline `store` tool's compress rate on `video` against the video class's own raw read rate from `probe-entropy-gate` (median of three passes, including file opens), with the gate costs and a like-for-like note printed beside it; G4, baseline `zstd/3` extraction against `7z/mx5` extraction blended over each mix. (6) The report prints a verdict proposal; the verdict itself is recorded by a person in D-08. — The report is the document the verdict rests on, so what it reads and how it derives each figure must be fixed in advance and visible in the output; the G3 proxy compares a cache-warm read-and-write pass with process start against an uncached read-only pass, which is why its definition is left to the owner rather than tuned to pass.
- D-24 — 2026-10-03 — **P0-3's "a second run differs by < 3% in time" is taken as met in substance by the second acceptance pair (`bench/results/2026-10-03-megatron`, `-megatron-2`; owner's call, option A of three).** The pair meets the round-trip and schema clauses twice over and 23 of its 28 compare totals agree within 3%; the five that do not have two causes outside the run loop: (1) the processor ran slower for part of run 1 — on `text-prose` the CPU seconds of 7z, zstd/19 and xz/9 grew in step with the wall time from one repeat to the next, which is a lower clock rather than another process taking cores, and run 2 showed the same once (xz/9 on `text-prose`); (2) single slow repeats of sub-second extractions on `game-assets` and `backup-versions`, in both runs at random positions, which three repeats absorb once but not twice. The D-21 remedy did what it was for: on `small-files` every repeat of `store`, zstd/3 and zstd/19 sits in one group in both runs and the runs agree within 2.5%, so the fallback named in D-21 is not needed. The clause itself is unchanged for future harness changes; an official measurement wants a steady processor clock and no other work on the machine, and its report says what ran. — Minute-long CPU-bound totals cannot agree within 3% on a machine whose clock varies by about 10% over half-hour windows, and sub-second totals cannot on a file system that occasionally stalls a repeat; another pair on the same machine would meet or miss the clause by the same accidents, and the harness has been shown free of the bias the clause exists to catch.
- D-25 — 2026-10-03 — **The dependency allow-list is final for Phase 0 and Phase 1: Apache-2.0, MIT, MIT-0, BSD-2-Clause, BSD-3-Clause, 0BSD, ISC, Zlib, CC0-1.0, Unicode-3.0, MPL-2.0 (as an unmodified dependency); LGPL only as a named per-crate exception (`cabac`); everything else, GPL included, is denied by absence.** `MIT-0` stays because `borrow-or-share` (via `jsonschema`, the result validator) offers nothing else and the licence is MIT minus the attribution clause; `Apache-2.0 WITH LLVM-exception`, `Unicode-DFS-2016` and `BSL-1.0` were removed from `deny.toml` because `cargo deny check licenses` passes without each of them (every crate that offers one also offers an allowed alternative). Adding a licence to the list is a recorded decision, not a convenience edit. — An allow-list that carries entries nothing needs stops being a statement of what was examined; cutting it to the tree's needs makes the next addition visible.
- D-26 — 2026-10-03 — **LGPL boundary.** Closed-source code (the GUI Pro features of D-01) reaches an LGPL component only through the open-source engine, as a separate process or a DLL whose complete source is published; LGPL C sources (bzip3, packMP3 and the like, should they ever be wanted) enter only through a separately published crate with its own named `deny.toml` exception, never vendored into this tree; the open-source binaries that contain LGPL code satisfy the relink requirement by their published source and ship a prominent notice and copies of the GPL and LGPL texts (LGPLv3 section 4(a) and 4(b)). — LGPL's conditions attach to the binary that links the library; keeping every such binary open source and putting a process or DLL boundary in front of proprietary code is what makes `cabac` (and any later LGPL crate) usable without touching the open-core licensing of D-01.
- D-27 — 2026-10-04 — **Gates G2 and G3 of D-07 restated for Phase 1 (amends D-07; owner's decision with D-08).** G2: "≥ 2× smaller on the versioned-backup class" is measured on a versioned set whose versions together exceed the largest dictionary window of the measured incumbents (7-Zip Ultra and zpaqfranz `-m5` as configured in `bench/tools.toml`), so that solid compression alone cannot remove the cross-version redundancy; the set is added to the corpus specification by its own task (the owner approves its spec before it is built), and the gate is evaluated with real LitePack archives through `lpk-bench run`, against the best measured incumbent on that set. G3: "video class stored at ≥ 80% of raw disk read speed" becomes "LitePack's store path (Fast tier) on the `video` class reaches at least 80% of the `store` control's compress throughput in the same `lpk-bench run` on the same machine" — a plain copy through tar is the speed the disk allows for reading and writing, and the incompressibility gate's cost is inside that figure. — On the Phase 0 corpus the versioned class fits in one dictionary window and the read-plus-write proxy cannot reach 80% of a read-only rate; both gates were measuring their own definitions rather than the method (D-08).
- D-28 — 2026-10-04 — **`.lpk` v1 frame grammar and header (E1-1; `crates/lpk-format`, `docs/spec/lpk-v1.md` §1–3).** Little-endian fixed-width integers; lengths as canonical unsigned LEB128 `u64` of at most 10 bytes (the last byte of a multi-byte varint is never 0x00; a tenth byte, if present, is exactly 0x01). Magic `89 4C 50 4B 0D 0A 1A 0A`. A 32-byte header: magic, `version_major: u16` (1), `version_minor: u16` (0), `flags: u32` (bit 0 `ENCRYPTED`, bit 1 `LISTABLE`, the rest reserved and zero), `archive_id: [u8; 16]` chosen by the writer; the reader checks length, then magic, then major (only 1; any minor), then flags. Frames: `kind: u16`, `flags: u16` (bit 0 `MUST_UNDERSTAND`, the rest reserved and zero), `payload_len: varint`, payload, BLAKE3-256 of the payload. Kinds 1 EntryTable, 2 ChunkData, 3 Records, 4 Recovery, 5 Index, 6 Trailer; 0 invalid; 7–0x7FFF reserved; 0x8000–0xFFFF experimental and never written. An unknown kind is skipped with its hash still verified unless `MUST_UNDERSTAND` is set, which is an error; a hash mismatch is always an error; truncation is reported by part (`header`, `frame header`, `payload`, `hash`; the brief's separate `magic` name was dropped when the header read became length-first); a reader limit on the payload length (default 1 GiB until E1-5 ties it to the decode envelope) is checked before anything is allocated, and buffers grow only as bytes arrive. — The PNG-style magic catches line-ending conversion and DOS `type`; per-frame hashes localise corruption and let a reader skip what it does not know; canonical varints make every encoding unique so hashes and signatures over encoded frames are well-defined; checking the major version before the flags lets a later major redefine them.
- D-29 — 2026-10-04 — **`.lpk` v1 entry table (E1-2; `crates/lpk-format/src/entry.rs`, spec §4).** The payload of an `EntryTable` frame is `entry_count` (varint) followed by the entries **sorted by path bytes, unsigned order, no duplicates**; a reader bounds the count by the bytes that remain (the smallest entry is 14 bytes). An entry: `kind: u8` (0 File, 1 Directory, 2 Symlink; others refused), `flags: u16` (bit 0 EXECUTABLE, 1 HIDDEN, 2 READ_ONLY, 3 SYSTEM; the rest reserved and zero), the path (varint length, UTF-8, `/` separators, non-empty components, no `.` or `..` component, no leading or trailing `/`, no `\`, no NUL, at most 65,535 bytes; each violation has a named reason), `mtime_ns: i64` (nanoseconds since the Unix epoch, `i64::MIN` = unknown), `size` (varint: a file's bytes, 0 for a directory, a symlink's target length), then for a symlink its target bytes (no NUL, 1–65,535) and for a file its chunk list (varint count, varint chunk indices into the archive's chunk list of E1-3). Readers stream the table (parse reads the count; entries are decoded on iteration) and report a directory with a non-zero size as inconsistent; writers also refuse chunks on directories and symlinks and mismatched targets. Trailing bytes after the last entry are an error. Open point for the extraction task (E2-19/E3): the path rules allow `:` and Windows-reserved names (`CON`, trailing dot or space, `C:` as a component); the extractor must map such names and must never let a component replace the target directory — the spec says so, the rule itself is written there. — Sorted unique paths give a canonical table (hashes and comparisons are meaningful, lookups can stop early); streaming keeps a million-entry archive within the payload's memory; nanosecond `i64` times cover every file system in use; counting bytes before entries makes a hostile count harmless.
- D-30 — 2026-10-04 — **`.lpk` v1 chunk table and Merkle tree (E1-3; `crates/lpk-format/src/{chunk,merkle}.rs`, spec §5).** A chunk record is `plain_len` (varint) and the BLAKE3-256 of the chunk's *original* bytes (what the user gets back, never the compressed or encrypted form); the chunk table is a count then the records, the count bounded by the bytes that remain (33 per record), streamed on read. The Merkle tree has the RFC 6962 shape without padding: leaves are the chunk hashes in table order; a tree of `n` leaves splits at the largest power of two below `n`; an internal node is `blake3::derive_key("LitePack lpk v1 Merkle node", left || right)`; the empty tree's root is `derive_key("LitePack lpk v1 Merkle empty", [])`; roots are 32 bytes; an inclusion proof is the RFC 6962 audit path and a verifier takes the leaf count from the chunk table, since the path alone cannot bind it. A file is verified by its entry's chunk indices: the lengths must add up (without overflowing) to the entry's size and each chunk's bytes must hash to the table's value, with the failing chunk named; a byte range is verified by reading only the chunks that overlap it. The spec carries the empty-root and two-leaf hex vectors. — Hashing the original bytes makes verification independent of codec, cipher and container details; the 6962 shape needs no padding and keeps proofs at `ceil(log2 n)`; derived keys separate node hashes from leaf hashes so no leaf can pose as a node; per-chunk hashes localise corruption and let a range be checked without reading the file.
- D-31 — 2026-10-04 — **`.lpk` v1 index and trailer (E1-4; `crates/lpk-format/src/{index,archive}.rs`, spec §6).** The `Index` payload holds, in order: the chunk table (D-30), its Merkle root (recomputed by every reader), the block table (per `ChunkData` block its frame offset and whole encoded length, first chunk, chunk count and plain length; blocks partition the chunk list contiguously in ascending order, lie between the header and the index without overlapping each other or any other recorded frame, and at most one block may be empty, only when the archive has no chunks), then the locations of the `EntryTable` frame and of the optional `Records` frame (zeros when absent). The `Trailer` frame is the archive's last 109 bytes: a frame of kind Trailer with empty flags and a fixed 72-byte payload — index offset, index frame length, BLAKE3 of the index payload, generation (0 unless appended to), the archive id. A reader opens an archive by reading the 32-byte header and the 109-byte tail, then the index at the recorded place (its payload hash must equal the trailer's, every recorded location must be at least 37 bytes — the smallest frame — and a recorded frame is read within its recorded length, never beyond it), and reads the entry table only when asked. If the tail is not a well-formed trailer, the reader walks the frames from the header: a chain that verifies to the end without a trailer is reported as truncated; a frame that fails its hash is reported as corrupt; bytes after a valid trailer are an error; a last frame that is a trailer of the wrong shape is `NoTrailer`. A one-pass chunk index gives O(1) chunk lookup and cumulative plain offsets; a reader holds at least 82 bytes per chunk once open. — A fixed-size tail lets a reader find and authenticate the index without touching the body; bounding every read by what the index recorded keeps a flipped length byte from being mistaken for truncation; distinguishing a clean cut from corruption is what makes journaling's rollback-by-truncation and recovery records meaningful.
- D-32 — 2026-10-04 — **`.lpk` v1 decode envelope (E1-5; `crates/lpk-format/src/envelope.rs`, spec §6–7).** The index carries, after the Merkle root, six varints: `max_window` (largest match-finder window any block needs), `max_bwt_block` (largest BWT block, 0 if none), `max_block_plain` (the largest block's plain length — must equal the block table's maximum), `max_frame_payload` (an upper bound on every recorded frame's payload: index, blocks, entry table, records — a recorded frame length `L` is admissible iff `L <= M + 36 + varint_len(M)`), `decode_memory` (the writer's estimate of one decoding thread's peak memory) and `threads_hint` (how many blocks may be decoded at once under that memory; 0 = none). A reader holds `Resources` (default window 256 MiB, BWT block 64 MiB, block plain 1 GiB, frame payload 1 GiB, memory 2 GiB — the method document's caps as reader policy, not format limits) and refuses, before reading any block, with `Refusal { field, needed, allowed }` naming the first field the archive exceeds; a caller overrides only by passing larger resources. Until the index is read the frame limit is the reader's own; after it, the smaller of the envelope's and the reader's. The index payload counts towards `max_frame_payload` although it contains the envelope's own varints, so a writer iterates until the value fits. — Declaring resources up front lets a 4 GB laptop or a NAS refuse an archive it cannot decode with a clear message instead of thrashing; keeping the caps in the reader rather than the format lets a bigger machine open a bigger archive without a format change; bounding every frame by a declared size keeps a hostile header from driving allocations.
- D-33 — 2026-10-04 — **`.lpk` v1 primitive set and decode graph (E1-6; `crates/lpk-format/src/{registry,graph,decode}.rs`, spec §8).** Thirteen primitives with 16-bit IDs: 0 `store`, 1 `zstd` (window log 10–31, 32-byte prior id), 2 `lzma` (dictionary size, lc/lp/pb), 3 `bwt` (block size, not zero), 4 `bcj-x86`, 5 `bcj-arm64`, 6 `delta` (base chunk, patch format), 7 `jpeg-reconstruct`, 8 `deflate-reconstruct`, 9 `png-filter`, 10 `base64` (variant, line length), 11 `utf16` (endian, BOM), 12 `container-reconstruct`; 13–0x7FFF reserved; 0x8000 and above experimental and never written. A block's decode graph is a chain of 1–16 steps (ID, zero flags, parameters of at most 256 bytes) applied in order to decode; an unknown ID stops the reader before any data is read (D-03), and every step is validated and known to be implemented before the first runs. The `ChunkData` payload starts with the graph, the plain length and the encoded length. Intermediate outputs are bounded by the envelope's largest block; the last step must produce exactly the plain length. The reference decoder implements `store` now and gains `zstd` and `lzma`; the reconstructions and transforms belong to the full reader and are reported as unimplemented. — A fixed, enumerated registry is what makes 'no executable decoder' (D-03) concrete: an archive can only name what the published spec defines, and a reader knows before touching data whether it can decode a block.
- D-34 — 2026-10-04 — **Writing and reading a `.lpk` archive; the reference tool (E1-7; `crates/lpk-format/src/{writer,reader,cli}.rs`, spec §9).** An archive is written as a stream, never seeking: header, then `ChunkData` blocks as they fill, then the entry table, the index and the trailer. The writer cuts each file into chunks through a streaming chunker (`feed(bytes, eof)`; a chunk never exceeds the configured chunk size, the writer refuses a chunker that returns a longer cut, and chunks never cross files), closes a block before it would exceed the block size, validates and requires sorted entries, fills the envelope from what it wrote, and refuses every further call after an I/O error or a bad cut (the archive is abandoned). Defaults: 1 MiB chunks, 64 MiB blocks, the `store` graph; the decode-memory estimate is one block's plain length and excludes the encoded input. A reader extracts a file by decoding each block once (one-block cache) and verifying every chunk against the chunk table as it writes; `verify` reads and checks every block and then checks every entry's chunk list and size against the chunk index without re-reading blocks; a block frame whose hash fails is reported by `verify` as that frame's hash mismatch and by `extract` as a mismatch of the requested chunk. A hostile chunk list that alternates between blocks defeats the cache — an open item for a decode budget. The reference tool `lpk-decode` (list, verify, extract, info) never overwrites a file, reuses existing directories, removes a file it created but could not finish, refuses symlink entries, joins paths one component at a time, escapes control characters when listing, and refuses Windows device names after trimming trailing spaces and dots from the stem: CON, PRN, AUX, NUL, COM1–COM9 and COM¹–COM³, LPT1–LPT9 and LPT¹–LPT³, CONIN$, CONOUT$, any component containing `:` or ending in a dot or a space (amends the D-29 list). Exit codes 0, 1 (verification or extraction error), 2 (usage or I/O). Consecutive chunk numbers per file are this writer's behaviour, not a format rule. — Streaming writes make pipes and single-pass archiving possible; verifying while extracting means a user never gets a wrong byte without an error; refusing device names at the tool, not in the format, keeps the format portable while the Windows tool stays safe.
- D-35 — 2026-10-04 — **zstd in the reference decoder, priors by id, the writer's encoder hook, test vectors (E1-8; `crates/lpk-format/src/zstd.rs`, `priors`, `tests/vectors/`; spec §6, §8, §10, §11).** The reference decoder decodes `zstd` blocks in pure Rust (`ruzstd`, MIT): it refuses before reading when the step's window log exceeds the reader's window limit, treats a frame whose header declares a window above the declared log as bad parameters, bounds its output by the expected length and the largest-block limit, and reports the library's own errors as `ZstdError`. A prior (D-10) is identified by the BLAKE3-256 of its bytes; for zstd a prior is a zstd-format dictionary (with the dictionary magic). The index lists, after the envelope, the sorted unique ids of every prior any block names; a block that names an unlisted id is refused when its header is parsed, and a listed id the reader's prior store lacks is `MissingPrior` before any decoding. The reader never fetches a prior; a store is the caller's (`lpk-decode --prior`). The index envelope is also checked against each block's graph when its header is parsed: a graph needing more window or BWT block than declared is an envelope mismatch. The writer takes a `BlockEncoder` (default `store`); the crate's own tests encode with the C zstd library as a dev-dependency only, and the production zstd encoder belongs to `lpk-core`. Committed test vectors (`zstd-basic`, `zstd-multiblock`, `zstd-dict` with its prior, `zstd-window`) are checked by decoding and comparing contents; the only test that regenerates them byte for byte is ignored, because that depends on the zstd library's version. — A decoder free of C keeps the reference small and sandbox-friendly; listing priors in the index lets a tool say what an archive needs before decoding; refusing on the envelope at header parse keeps resource refusals up front instead of mid-extraction.
- D-36 — 2026-10-04 — **LZMA in the reference decoder (E1-9; `crates/lpk-format/src/lzma.rs`, spec §8, §11).** The `lzma` primitive's encoded bytes are a raw LZMA1 stream (no `.lzma` header) that may or may not end with the end-of-payload marker; a decoder stops when it has produced the block's plain length — input left after that is "trailing input", a stream that ends early is "truncated", a match that crosses the bound is a payload overrun. The first range-coder byte must be zero; the final code-is-zero check applies only when a marker is present, and a decoder must not refuse a marker-less stream for it. A match distance greater than the dictionary size or than the bytes produced so far is an error, and the decoder's buffer is the smaller of the dictionary size and the plain length, so whether a stream decodes never depends on the reader's window limit; the dictionary size itself is refused up front when it exceeds that limit. Parameters follow D-33 with one more rule: `lc + lp <= 4` (liblzma's `LZMA_LCLP_MAX`, the literal-table bound), which leaves `lc` 5–8 unreachable though the layout allows them. The crate is `lzma-rs` pinned to `=0.3.0` (MIT, pure Rust, `raw_decoder`; unmaintained since 2023 — a known risk for the fuzzing task, and the pin exists because the decoder reads one of its error texts to tell an overrun from a short stream, with a generic error as the fallback). The test encoder is the `liblzma` crate as a dev-dependency only; three committed vectors (`lzma-basic`, `lzma-multiblock`, `lzma-props`) are checked by decoding. — A raw stream with explicit properties keeps the block header the single source of parameters; stopping at the plain length makes the end marker optional and the decoder robust to either encoder habit; sizing the buffer by the declared dictionary keeps acceptance a property of the archive, not of the machine reading it.
- D-37 — 2026-10-04 — **`.lpk` v1 reconstruction records (E1-10; `crates/lpk-format/src/record.rs`, spec §12; amends D-33).** The `Records` frame holds a count and then records in id order, each with its kind (the reconstruction primitive it serves: 7 jpeg, 8 deflate, 9 png-filter, 10 base64, 11 utf16, 12 container), zero flags, a body length, the body and the body's BLAKE3; counts, byte-string lengths, body lengths and chunk indices are varints, fields with a stated width are fixed-width little-endian. The six reconstruction primitives' parameters are now a single record id (D-33's layouts for ids 7–12 are replaced; base64 and utf16 settings live in their records), checked against the record count when a block header is parsed. Every body ends with the BLAKE3 of the original bytes it rebuilds — the inversion's verification target; the reference decoder validates records (hashes, enumerations, length arithmetic, the assembly rules) but applies none, as the libraries that apply them belong to the full reader. Assembly rules: a container's original is its framing bytes with each member's original bytes inserted at its offset, members ascending and non-overlapping, framing plus members equal to the original length; a JPEG's primary image ends at `primary_len`, raw trailing data is everything after it, and when the trailing data is peeled the gain-map secondaries and the nested trailing chunks cover the rest exactly (gain-maps can be peeled only when the bytes between them go into nested chunks); base64 line fields and png filter counts must agree with each other. Chunks a record names must exist and must lie in blocks with a strictly lower index than any block whose graph names the record (no cycles), which `verify` checks; the reference writer validates records before writing them. — Per-record hashes locate corruption without decoding; verification targets make 'bit-exact inversion' testable per stream (D-09); the block-order rule keeps a full reader's recursion finite.
- D-38 — 2026-10-04 — **`.lpk` v1 recovery frames (E1-11; `crates/lpk-format/src/recovery.rs`, spec §13; applies D-11).** Recovery is Reed-Solomon in GF(2^16) over fixed-size shards (a multiple of 64 bytes; 64 KiB by default, at most 16 MiB), computed with `reed-solomon-simd`, in **groups**: the writer collects whole data frames (`ChunkData`, `EntryTable`, `Records`) into a group of at most `group_shards` shards (2048 by default; a group's bytes at most 1 GiB; a frame larger than a group is refused), and when the group closes it writes that group's recovery frame right after it — so recovery frames are interleaved with the data they protect, each covering exactly the frames since the previous one, ascending, disjoint, tiling every data frame and never covering a recovery frame, the index or the trailer. A recovery frame holds the coverage range, the shard length, the real shard count and the encoder's count, the recovery count (`ceil(count × percent / 100)`, `percent` 1–20, at least 1), the BLAKE3 of every data shard (damage is located shard by shard without decoding) and the recovery shards. Repair writes a repaired copy: per frame, shards whose hash fails are rebuilt when they are no more than the recovery count, verified by hash, and written; a frame beyond its capacity is reported as unrepairable with its numbers while the other frames are still repaired; a recovery frame whose own hash or fields fail is counted unusable and skipped. Memory is bounded by one group on both sides — the writer holds the open group's bytes, one encoder work buffer and one group's recovery shards (the three coexist only while a group is encoded); repair holds one group's decoder buffer, refused up front when it would exceed the reader's memory — and the writer refuses options whose group could not be repaired within the default memory. — A single frame over the whole archive would have cost the whole archive in RAM, because the coding library copies every shard it is given; fixed groups make both writing and repair stream, and per-shard hashes make the damage map cheap. The 'PAR3-style block layout' of the method document is this grouping.
- D-39 — 2026-10-04 — **`.lpk` v1 encryption (E1-12; `crates/lpk-format/src/crypto.rs`, spec §14; applies D-06).** Suites: 1 AES-256-GCM (default), 2 XChaCha20-Poly1305; 32-byte keys, 12- or 24-byte nonces, 16-byte tags. The payloads of `ChunkData`, `EntryTable` (unless listable), `Records` and `Index` frames are sealed — nonce, ciphertext, tag — and carry frame flag bit 1 `SEALED`; the frame's BLAKE3 is over the ciphertext, so integrity and recovery work without a key; `Header`, `KeySlot`, `Recovery` and `Trailer` are never sealed. A random 32-byte archive key seals every frame with a nonce derived by HKDF-SHA256 from the key, the archive id, the frame kind and the frame's sequence number (its position among all frames, recorded in the index; the index itself under `2^64 − 1 − generation`); the associated data binds the archive id, kind, sequence and sealed length. The key slot (frame kind 7, first after the header) holds the suite, Argon2id parameters (defaults t 3, m 64 MiB, p 4; t and p bounded 1–64, m refused above the reader's memory), a 16-byte salt, the keyfile flag, the archive key wrapped under the Argon2id-derived KEK (with a keyfile: HKDF of the Argon2 output and the keyfile's BLAKE3) using a zero nonce used exactly once and an associated-data string that includes the header flags, and a keyed-BLAKE3 check value. The index records the BLAKE3 of the entry table as stored, so a table swapped under the correct password is refused; listable mode leaves only the entry table in clear (unauthenticated until the key opens the index). A wrong password fails at the key slot before any other frame is read. Without credentials an encrypted archive opens keyless: recovery frames are found by walking the frame envelopes, so `check`, `repair` and a hash-only `verify` work on the sealed bytes; extraction needs the key. Secrets are zeroized; passwords are raw bytes without normalisation. — Derived nonces remove the one failure mode of random nonces; sealing payloads but not envelopes keeps integrity, skipping and repair possible without a key, which a damaged encrypted backup needs; binding the header flags into the key wrap stops a listable-mode downgrade.
- D-40 — 2026-10-04 — **`.lpk` v1 generations (E1-13; `crates/lpk-format/src/{writer,archive,journal}.rs`, spec §6 and §15).** An archive grows by appending a generation after the last trailer: new blocks (with their recovery frames), a complete entry table, records, a complete index describing every chunk and block of every generation (chunks only deleted entries referenced stay listed), and a new trailer whose payload now holds the previous trailer's offset and a random 16-byte generation salt (payload 96 bytes, frame 133). The index carries a generation table (number, start offset, first sequence, salt); frame sequence numbers are positional and continue across generations; every sealed frame's nonce is derived with its generation's salt as well, and the index of generation g under the reserved sequence `2^64 − 1 − g`, so a rollback followed by a different append never repeats a nonce under the same key. An append to an encrypted archive must unwrap the key slot with the credentials given; old reconstruction records must be unchanged at their positions; recovery coverage is checked against the generation table's start offsets, never against old trailer bytes, and ends at the index or at the previous trailer. The writer dedups new chunks against the old chunk table by hash and length. Rollback truncates to an earlier trailer after verifying the whole chain (strictly decreasing offsets, generation minus one per step, hashes and archive id); a cut append is diagnosed as truncated and rolled back the same way; the file is synced before and after the trailer, which is the commit. — Append-only generations give incremental backups and version history in one file (D-07's versioned sets, zpaq-style); per-generation salts are what make 'rollback then append' safe under one key, a case the first design missed; checking coverage against the authenticated index keeps a flipped byte in an old trailer from disabling a whole recovery group.
- D-41 — 2026-10-04 — **`.lpk` format v1 is frozen (E1-14).** The specification `docs/spec/lpk-v1.md` as merged with E1-14, with `docs/spec/CONFORMANCE.md` and the committed vectors, is format v1: a change to any byte layout, rule, derivation or error class from here on is a new format version, not an edit. The evidence of the freeze: a read-only read-through by a reviewer who had not seen the code (its findings applied in a fix round with recorded rulings, including the normative citation of RFC 8878 for zstd frames and the LZMA SDK's specification for LZMA1, numbered check orders, one error catalogue, and a statement of what each check authenticates); an independent decoder (`crates/lpk-check`) written from the specification and the vectors alone — its author attests to the files read — which passes the conformance gate on every vector; fuzz targets for every reader path (`fuzz/`, run on Linux CI) and a seeded mutation test in the normal suite. Two things are stated as such in the text rather than defined: primitives 3–12 (BWT, the BCJ filters, delta and the six reconstructions) have fixed ids and parameter layouts but no decoding meaning in v1 — a v1 writer must not emit them and a v1 reader reports them unimplemented; their normative sections come with the Phase 1 tasks that implement them, each as a format revision; and the Reed-Solomon construction of §13 is defined by reference to `reed-solomon-simd` 3.x (the normative description is PLAN task E1-15), so an independent reader may report damage from the shard hashes without implementing repair. — A format earns its freeze when a second implementation can be written from the text; the gate did that, and the gaps it found are now either closed or named.

- D-44 — 2026-10-04 — **`lpk-core` ingest and the store path (E2-1; `crates/lpk-core/src/{ingest,source,store,error}.rs`).** (1) Every file is read through a plain buffered `File`, whatever its size: the memory map that the task's wording foresaw above a threshold is not used — the writer copies every segment into its own buffer anyway, and a mapped read turns an I/O failure or a truncation by another process into a process fault (SIGBUS, EXCEPTION_IN_PAGE_ERROR) instead of an error naming the file; it may return when a later task measures a need, and then only behind a `*-sys` crate. (2) The walk (an explicit-stack walker, no recursion) produces the archive's inputs sorted by path bytes without duplicates, validated with the format's path rules before anything is written; an unportable or non-UTF-8 name, a duplicate path and a special file (socket, FIFO, device) fail the walk with the exact path — nothing is skipped silently; hidden entries are excluded before validation when `include_hidden` is off; the root's own name never appears. (3) Symlinks (and Windows junctions) are recorded with their raw target bytes and never followed unless `follow_symlinks` is on, in which case a visited set of directory identities bounds the walk (a cycle or a second route records the link instead of descending again, a dangling link is recorded), and `one_file_system` keeps the walk on the root's volume. (4) Between the walk and the read a path may have been swapped: reads are bounded to the walked length plus one byte (`ChangedWhileReading` on growth), Unix opens with `O_NOFOLLOW | O_NONBLOCK`, and on both platforms the opened object must be a regular file with the identity the walk recorded (`dev`/`ino` on Unix, `same_file` volume and index on Windows) — Windows does not open with `FILE_FLAG_OPEN_REPARSE_POINT`, because that would read cloud-file placeholders, deduplicated and WOF-compressed files past their filters. (5) `archive_store_file` creates the target with create-new, never archives the archive itself, and installs the writer's sync so the trailer that commits the generation reaches the disk after the data. — Reviewed read-only in two rounds (the mmap recommendation and the swap, growth, sync and silent-skip findings); the many-small-files cost of the identity open on Windows is accepted for now and noted for the speed work.
- D-45 — 2026-10-04 — **The classifier and the incompressibility gate (E2-2; `crates/lpk-core/src/{classify,gate}.rs`).** (1) `Class` has eleven routing labels: the nine of the PLAN (`Text`, `Jpeg`, `DeflateContainer`, `Png`, `Executable`, `Audio`, `ImageRaw`, `HighEntropy`, `Other`) plus `Video` and `Compressed` for already-compressed containers that skip the gate and every peel. (2) `classify` decides by magic bytes first — every row carries a second check so that text cannot match it (`PE\0\0` must actually be read for `MZ`; `GIF87a`/`GIF89a`; a valid ID3 header; a second MPEG frame header; a digit after `P1`..`P6`; gzip's method byte; BMP's reserved zeros; `BZh` plus a digit; `ftyp` brands sorted into audio, image and video) — then by byte statistics on the first 64 KiB: `Text` when there is no NUL, the sample is UTF-8 up to one truncated trailing sequence and control bytes are below half a percent; else `HighEntropy` when the gate says so; else `Other` (UTF-16 with a BOM is `Other` until the text-encodings task). (3) The gate is two-stage, with the Phase 0 probe's sampling (the first 4 KiB of every 64 KiB window): a sample below 7.5 bits per byte is compressible without a second pass; otherwise the whole block's order-0 entropy decides at 7.95 bits per byte; both are parameters of `Gate` with those defaults, read off the entropy-gate tables of the Phase 0 report (`bench/reports/phase0-2026-10-03.md`: the 7.95 entropy gate has the best precision of the grid on every class and near-complete recall on video and random data; a sample under 7.5 is almost never an incompressible block). (4) What the corpus tests assert: the classifier table test labels every file of every class of `small` as its extension predicts (one checked exception: "log" files of the small-files class that hold raw non-UTF-8 bytes are `Other`); the gate test reproduces the probe's ground truth (xz preset 9 keeping at least 95% of a 1 MiB block) and asserts the method's guarantee on any profile — no false negative on video or random data comes from the sample stage — plus full recall on random data, no false positives on the six classes the Phase 0 table shows clean, and a 99% video recall floor only on the `full` profile, the one Phase 0 measured; on `small` two video blocks sit just under the whole-block threshold and the recall is printed, not asserted. — The thresholds are measured choices, not tuning; precision is what keeps the size (a stored block that would have compressed), recall is what keeps the time, and the Fast tier's own compressor stores a block that does not shrink, so a missed block costs time only.
- D-46 — 2026-10-04 — **The reference writer's API for the pipeline (E2-3, first half; `crates/lpk-format/src/writer.rs`; no format change).** (1) A `BlockEncoder` returns, per block, `Encoded { graph, bytes, resources }`: the graph is chosen block by block (the format records each block's graph in its header), validated when the block closes with the same checks the writer applied once at construction before, and an invalid graph abandons the archive like an I/O error; the index's prior list is the sorted set of every prior any block's graph names, and the envelope is the maximum over the blocks of the encoder's reported resources and the graph's own registry resources (an archive with no data block declares the envelope of no block, where it used to declare the graph's window); an encoder error of any class abandons the archive like an I/O error. (2) `add_file`, `add_directory` and `add_symlink` may be called in any path order: the writer sorts the entry table when it finishes (and when an append merges), and a second add of the same path is `DuplicateEntry` at that call; the reader's `UnsortedEntries` check is unchanged. (3) `Writer::close_block` ends the current block early (a no-op when it holds no chunk), so a block never has to span two clusters of files. The committed vectors are reproduced byte for byte, and the spec's error catalogue gains the writer refusal `DuplicateEntry` (an editorial row, recorded in `docs/spec/CHANGES.md`). — The Fast tier stores incompressible blocks and compresses the rest with or without a dictionary, feeds files in cluster order rather than path order, and wants a block boundary at each cluster change; all three are freedoms the frozen format already has and the reference writer did not expose.
- D-47 — 2026-10-04 — **The Fast tier (E2-3; `crates/lpk-core/src/{fast,cluster}.rs`).** (1) The modeller is zstd through libzstd (the `zstd` crate), level 3 with a 2^27-byte match window and long-distance matching, content size written and zstd's own checksum off (the format hashes every frame and chunk); level and window are parameters of `FastOptions`; each block's step declares the smallest window that holds it (a frame whose content fits its window is single-segment, so its `Window_Size` is its content size), which keeps a small archive's envelope small. (2) Blocks are decided one by one: a block of a `HighEntropy`, `Video`, `Compressed`, `Jpeg` or `Png` cluster is stored without a test; any other block is stored when the gate of D-45 calls it incompressible or when zstd's output is not smaller than the input, and compressed otherwise; the counts of each case are reported. (3) Files are fed in clusters — grouped by class and, inside `Text`, by the kind of text the extension suggests (prose, structured, source), prose first and the incompressible classes last, path order inside a cluster — with a block boundary at every cluster change (D-46), so a block never mixes kinds. (4) No dictionary is bundled. The PLAN's "per-class dictionaries bundled as priors" was built and measured on `small`: with solid 64 MiB blocks the archives of every large text class came out larger with the trained dictionaries than without, and the gains elsewhere were a few kilobytes (the task report holds the table), while a zstd dictionary carries verbatim fragments of its training samples into every binary that ships it; the mechanism stays — a caller may provide a dictionary (`DictionaryPolicy::Provided`), extraction takes priors from files, and the path is tested with a dictionary trained at test time — and it is to be re-measured if a small-block or per-file mode is ever added. (5) The PLAN text's BCJ/ARM64 filters are not in this tier: `bcj-x86`/`bcj-arm64` are primitives the frozen v1 forbids a writer to emit until a format revision specifies their decoding; they come with that revision. (6) libzstd is now a runtime dependency of the engine (BSD-3-Clause); its notice is owed in the third-party notices of every binary distribution (`docs/LICENSING.md`). — The tier's purpose is speed with a sensible size; every stored-block rule costs nothing on size and saves time, and a dictionary that does not shrink the archive is not worth its bytes in every decoder.
- D-48 — 2026-10-04 — **The pipeline struct, the `lpk` tool and how the harness measures it (E2-4; `crates/lpk-core/src/pipeline.rs`, `crates/lpk-cli`, `bench/tools.toml`, `crates/lpk-bench/src/report`).** (1) `Pipeline` fixes the stage order classify → peel → fold → model → seal, with Fold defined as running on peeled streams; peel and fold are empty trait slots until their tasks land, the model is `Store` or `Fast`, and `archive_store`/`archive_fast` are thin fronts over the one code path. (2) The command-line tool is `lpk a <archive> <dir>` (create-new, the directory's contents, the Fast tier by default, `--store` for the control path), `lpk x <archive> <outdir>` and `lpk t <archive>` (the format tool's own extraction refusals and `verify`, called, not copied; dictionaries only from `--prior` files, D-47); exit codes 0, 1 (usage), 2 (refused or failed, naming the file); never a prompt; `lpk --version` prints `lpk <version>+<git hash>[-dirty]` so every measurement names the exact build. (3) The catalogue row `lpk` is a directory-mode tool with a flat layout, the workspace's release binary found through a relative hint tried before PATH, settings `fast` and `store`, and no thread dependence of the ratio; the runner treats it like every other tool. (4) The report may pool several `--results` directories of one corpus on one host: every directory validated and release-built; each row, tool entry and run setting cited to its own file; a tool's version taken from the directory that holds its rows; refused when two directories hold rows of one combination or of one tool at two versions, when `dedup` flags disagree, or when thread counts differ (the last only without `--allow-unclean`, which marks the report); a `tools.json` from before D-43 is read as "dedup unknown" and takes the other directory's flag; a dirty, unknown or stale `lpk` build (its hash not that of the directory's runner) is an unclean reason. — Incumbents measured once on the `full` profile cost seven and a half hours; pooling lets every later `lpk` run be compared against them without re-measuring, with the provenance of each number kept, and the refusals keep anyone from picking the better of two measurements of the same thing.
- D-49 — 2026-10-04 — **How a reserved primitive gets its decoding (the format revision process; first used by E2-5).** The frozen v1 (D-41) gives primitives 3 to 12 an ID and a parameter layout but no decoding, and forbids a writer to emit them. A revision that adds one: (1) raises the specification's minor version (the header's `version_minor`; a reader of an earlier minor accepts the archive and reports `UnimplementedPrimitive` on the blocks that use the new primitive, so every earlier reader fails safely and never silently); (2) states the step's input, output and resources in section 8, by citation when the codec is a published format with a maintained implementation (as section 8 cites RFC 8878 for zstd and the LZMA SDK for LZMA1): the Lepton format as `lepton_jpeg` implements it for `jpeg-reconstruct`, and likewise for the Deflate corrections of `preflate-rs` when their task comes; (3) adds a vector built by the reference writer with its expectations in `CONFORMANCE.md`, a negative expectation for the earlier reader, and a dated `CHANGES.md` entry; (4) keeps `lpk-format` the minimal reader (store, zstd, lzma) and puts the "full reader" of the reconstruction primitives in `lpk-core`, registered through the format's decoder registry with access to the archive's records and chunks; (5) passes the independent-decoder gate again: the author of `crates/lpk-check` — a fresh implementer who reads only the specification, the vectors and the named library's documentation — adds the primitive, and may use the named codec library for the codec itself while implementing the framing, the record assembly and the verification from the text alone; (6) is recorded as a decision with the task that needed it. — A reconstruction codec such as Lepton is thousands of lines of arithmetic coding that no second implementation would reproduce bit for bit from prose; what the specification must make independently implementable is everything around the codec — which bytes go in, which come out, how the record reassembles the original and what is verified — and the minor-version rule keeps old readers honest about what they cannot decode.
- D-50 — 2026-10-04 — **The JPEG peel and format revision 1.1 (E2-5; `crates/lpk-core/src/peel/jpeg.rs`, `docs/spec/lpk-v1.md` revision 1.1).** (1) Revision 1.1 specifies `jpeg-reconstruct`: one Lepton stream per block, decoded by the format `lepton_jpeg` implements (named with its version range, as D-49 allows) into the primary image's bytes, then assembled with the record's trailing data and secondary images and verified against `original_hash`; the checks run in the order the reference performs them, a chunk a record names must lie in a lower block whose graph names no reconstruction primitive (writer and reader both refuse), and the header's `version_minor` is the revision the writer wrote under, not a per-archive fact. (2) The peel is fallback-first (D-09): a file that classifies as JPEG is read once, whole, only when it is below a size cap (the library's own file-size cap; larger files take the streaming path and count as a fallback); the marker scan finds the primary image's end and any secondary images; the Lepton stream must be smaller than the primary bytes and must decode back to them bit for bit before it is kept; every failure — progressive images the library rejects, four-component and arithmetic-coded images, the dimension and size caps, a verification mismatch, no gain, anything else — stores the file as-is and is counted with the Phase 0 probe's taxonomy, so the peel's outcome on the corpus can be read against the probe's; on `small` it recovers the probe's outcome exactly (the same files peeled, the same two progressive images stored as-is). (3) Trailing data and secondary images are written first as nested streams so their chunks lie in lower blocks, the record is added while writing, and the primary's block carries the graph naming it; the entry's chunk list stays in file order. (4) The writer's `decode_memory` for such a block is an allowance — the coefficient term computed from the frame header plus a fixed working-set term that this revision does not bound; the reader passes the smaller of the archive's and its own limit to the decoder, which refuses an image whose term exceeds it instead of decoding. (5) The Lepton stream's bytes depend on the zlib backend `lepton_jpeg` is built with (the workspace build uses the C zlib through `flate2`, a build of `lpk-core` alone the pure-Rust one), so the committed vector is byte-identical under the workspace build and checked structurally under another backend — never silently in CI; no backend is pinned, because vectors are not a normative encoding and pinning would put C zlib into the product for a test. — The peel is the product's pitch (G1), and every rule above exists so that it can never lose a byte: a Lepton stream that does not reproduce its image is never written, and nothing about a peeled archive is trusted on extraction without the original's hash.
- D-51 — 2026-10-04 — **The Balanced tier (E2-6; `crates/lpk-core/src/balanced.rs`; amends D-47 for this tier).** (1) The modeller is raw LZMA1 through liblzma with a 64 MiB dictionary (the dictionary 7-Zip Ultra's catalogue row uses, so the parity check compares like with like), `lc` 3, `lp` 0, `pb` 2, the deepest binary-tree search, the end-of-payload marker always written, the step declaring the dictionary the encoder actually used; blocks of 256 MiB. (2) Per block, zstd `--ultra` at the same window as the dictionary is the alternative: four stripes of the block are compressed by both candidates and the smaller sum wins, lzma on ties; the winner encodes the block and the no-gain fallback of D-47 still stores a block that does not shrink. (3) No entropy gate: the gate of D-45 is a speed device for the Fast tier, and order-0 entropy cannot see the cross-file matches a solid LZMA stream finds — on `small` it had stored a whole block of PDFs that 7-Zip Ultra compresses to about half — so in Balanced only the stored classes of D-47 and the no-gain fallback store a block. (4) Soft cluster boundaries: a block closes at a cluster change only once it holds at least half the dictionary, compressible clusters are fed first and the stored classes last, and a block that spans clusters keeps the hint of its first — a few-megabyte tree becomes one solid stream as in 7-Zip instead of several cold ones, while large trees keep cluster locality; the Fast tier keeps D-47's hard boundary. (5) The dictionary and the zstd window are bounded by the default reader's `max_window`, so the tier never writes an archive the default reader refuses; the encoder's memory is reported as liblzma's approximate query and the tier's need is stated qualitatively (compress: the block plus several times the dictionary; extract: the block plus the dictionary) until measured. — Parity with 7-Zip Ultra on the text classes is the acceptance; the two structural losses the first corpus run showed (the gate and the cold streams) were rules carried over from the speed tier, not properties of the coder, and the remaining gaps on the Deflate-bearing classes are the Deflate peel's to close (E2-10).

- D-53 — 2026-10-04 — **Fold's first stage: content-defined chunking and dedup (E2-7; `crates/lpk-core/src/fold/`, `crates/lpk-format/src/writer.rs`).** (1) The chunker is FastCDC (the 2020 variant, normalization level 1) with the Phase 0 probe's parameters — minimum 4 KiB, average 64 KiB, maximum 512 KiB — streamed per file through the writer's `Chunker` hook, so the cuts and the chunk hashes are exactly the probe's. (2) Dedup is global within an archive: a chunk whose BLAKE3 equals one already written is referenced by index, nothing goes to the block and no record to the chunk table; the index of hashes lives in the writer for the archive's lifetime (one entry per stored chunk — the memory task bounds it later); an append still deduplicates against the old table as before; the format needs nothing new (an entry's chunk list may reference any chunk, as section 9 says), and every committed vector stays byte-identical because dedup is off in `WriterOptions` by default. (3) Both tiers run the stage by default (`lpk a --no-dedup` returns to the fixed 1 MiB cut and no dedup); a JPEG whose whole content is already stored is never peeled, and a JPEG whose peeled part turns out already stored writes no stream and is counted apart; the hash index prefers a plain block's copy so a nested part equal to an earlier image deduplicates too. (4) The acceptance held exactly: on `backup-versions` of `small` the bytes the writer deduplicated equal the probe's "saved by chunk dedup" figure, and the same holds on every class (the task report; the archive sizes with and without dedup are printed there only). (5) From this task on, the catalogue's `fast` and `balanced` settings include dedup, so `lpk` rows measured before it are from a different build — the build hash in the recorded version tells them apart, and the pooled report never mixes two measurements of one combination. — Dedup costs almost nothing (the hashes were computed anyway) and is the first half of what G2 needs; the second half, deltas between near-duplicate chunks, is E2-9 and needs the `delta` primitive's format revision.
- D-54 — 2026-10-04 — **The extraction engine (E2-19; `crates/lpk-core/src/extract.rs`; the format reader's additive block API).** (1) Extraction is block-ordered: a plan maps every entry's chunk list to (file, offset) placements, the blocks are decoded in index order, each once, and every chunk is written to each place that needs it — a deduplicated chunk to several files, a file's later chunks to their offsets — so the number of block decodes is the number of blocks, whatever the entry order; the measured path-order extraction through the one-block cache had re-decoded a block per file (fifty minutes on the versioned class). (2) Blocks are decoded by a pool of workers ahead of the writers under a memory bound: blocks in flight times the envelope's `max_block_plain` (two blocks per worker when the archive has reconstruction records, whose nested parts come from a lower block) within the reader's decode memory; the fork of the index each worker holds is a cost outside that bound and documented as such; nested decodes are counted apart from block decodes. (3) `--threads N` is the extraction's whole thread budget: decoders plus file writers never exceed N, writers being one quarter of N between one and four, `N = 1` the sequential path — so the runner's rows compare `lpk x --threads N` with 7-Zip at the same N thread for thread. (4) Any failure anywhere — a decode or write error, a chunk that does not hash, a worker panic — cancels the pool, joins every thread, removes every unfinished file and keeps every finished one, then reports the error naming the block and an entry in it (a panic is re-raised after the cleanup); success is returned only when every placement of every file is complete; existing targets are refused before anything is written. (5) The safety policy is a hook (`ExtractPolicy`) whose default calls the format tool's own rules — unsafe paths, Windows reserved names, symlinks, overwrite — plus one rule of its own: a target whose existing parent chain below the output directory contains a symlink or junction is refused, so an extraction never writes outside its directory through a pre-existing link (opening relative to a verified directory handle is the stronger rule for E3/E6). (6) Files are created at their first write with create-new and their final length, and closed with their modification time once complete; flags and directory times are not restored, as the format tool does not restore them either. — Extraction speed is the Fast tier's promise (G4) and the one place where a mistake costs the user's data; the engine decodes each block once in parallel and never leaves a file it cannot vouch for.
- D-55 — 2026-10-04 — **File ordering inside clusters (E2-8): path order by default, extension order as an option, the similarity sketch not merged.** (1) Built and measured on `small` in two designs: super-features over chunk hashes (which cannot see files shorter than a few chunks — nothing sketched on `small-files`) and content-shingle min-hashes under twelve seeds in three super-features (which sketch files of any size): moving near-duplicate groups next to each other changed the Balanced archives of `software-installed`, `game-assets`, `small-files` and `source-git` by a few kilobytes either way — a wash — because every one of those classes fits inside the 64 MiB dictionary, where adjacency changes only the cost of coding a match distance; the extension order (7-Zip's) helped only the many-tiny-files class and hurt installed software, whose directory locality it breaks. - D-56 — 2026-10-13 — **Reconstruction records in an appended generation (the reference writer; unblocks E2-14).** (1) `Writer::append` loads the old `Records` table into its options, so `add_record` appends new records after the old ones, and an append writes a new `Records` frame only when it added or restated records — an append without records keeps the old frame's location and is byte-identical to before (the committed `journal-3gen.lpk` still equals its builder). The spec already said what such a frame must hold ("Layout of an append": every old record at its old position, unchanged); nothing in the byte format or in the spec's rules changed, `docs/spec/CHANGES.md` has no entry, and the independent decoder `lpk-check` decodes the new conformance vector `journal-record.lpk` (a generation 0 text file, a generation 1 peeled JPEG with its record) with its source untouched. (2) The writer closes the hole the old guard had papered over: a record's chunks may not lie in a block whose graph names a reconstruction primitive (spec section 12), and in an append it cannot see the old blocks' graphs — so it keeps the old archive and reads an old block's graph lazily, once, only when a record part would deduplicate against one of that block's chunks (the part is then stored anew) or when a closing block names a record whose chunk is old (`BadRecord`, `nested record`); an append that involves no record never reads an old block. The append constructors therefore take the old archive by value for the writer's lifetime (`R: 'static`). (3) The vector's generation 0 is written at header revision 1.1, because an append cannot raise the header's revision and the peel's primitive needs it: an archive made before 1.1 takes no peeled appends — the pipeline refuses that (`BadOptions`, `version_minor`) before writing anything. — The journal was specified to carry records from the start; the writer merely had not implemented it, and the only safe way to add it was to make the section 12 rule hold across generations rather than trust that no caller would hit it.
- D-57 — 2026-10-13 — **Encryption through the pipeline and the `lpk` tool (E2-12).** (1) `lpk a|x|t|check|repair` take `--password <str>` (documented as visible in the process list), `--password-file <path>`, `--keyfile <path>`; `lpk a` adds `--suite aes-256-gcm|xchacha20-poly1305` (default AES-256-GCM, D-39) and `--listable`, both requiring a credential; the password-file rule is the format tool's (one trailing newline, with a carriage return before it, is not part of the password; a keyfile alone is an empty password); the Argon2id parameters are the format's defaults; the password is moved into the format's `Credentials` (wiped on drop) and never printed or logged. - D-58 — 2026-10-13 — **Recovery records through the pipeline and the `lpk` tool (E2-13).** (1) `lpk a --recovery <percent>` (0 to the format's maximum; default 0 until the product default is decided) sets the writer's recovery percentage with the format's default shard and group sizes (D-38); `lpk check <archive>` and `lpk repair <in> <out>` run the format tool's `check` and `repair` (called, not copied); `lpk t` fails on a damaged shard as the format's verify does, and `lpk x` refuses a damaged archive rather than repairing it on the way (repair is an explicit step that writes a new file). (2) The bound is the spec's (section 13): per group, `ceil(data_shards × percent / 100)` shards, at least one, are repairable; the tests overwrite exactly that many distinct shards per group with random runs, repair, compare byte for byte, verify with the full reader and extract bit-exactly; one shard over the bound in any group is reported `Unrepairable` with the frame, the damage and the capacity, never silently "repaired", the other groups still repaired. - D-59 — 2026-10-13 — **The journal through the pipeline and the `lpk` tool (E2-14), with a negative result on the size clause.** (1) `lpk append <archive> <dir>` writes one snapshot generation in place: the archive is opened with the credentials first (a keyless or wrong-password open is refused before the file is opened for writing), the old entry table's paths are read, every old path absent from the appended tree is deleted (`Writer::delete_path`; the chunks stay in the table, as the spec's journal says), and the new tree goes through the same stage loop as a new archive — tiers, the JPEG peel with its records joining the old ones (D-56), the Fold dedup against the old chunk table (the writer's), ordering — so an unchanged tree appends with no new chunk; the archive inside its own root is left out of the walk by file identity; any failure after the file was opened for writing — an error or a panic — truncates it back to its original length through a separate write handle held by a drop guard (an append-mode handle cannot truncate on Windows, which the review caught), so the archive is the previous generation again; a truncation that itself fails is reported with the length the file was left at, never swallowed; and a generation cut short by the machine is recovered by `lpk rollback`. The tier flags of `lpk a` are shared with `append` (one builder), `append` takes `--recovery` as `a` does, `lpk rollback <archive> <generation>` and `lpk info` run the format tool's own code. (2) Generations are numbered as the format numbers them: `lpk a` writes generation 0, each append the next one; "rollback to v1" is rollback to generation 0, which reproduces v1 bit-exactly on the temp tree and on `backup-versions` of `small`. (3) The acceptance's size clause — the archive after the appends within the frame overhead of the one-shot archive of all three versions — holds on a temp tree whose changes are noise and does not hold on `backup-versions`: the chunk-level dedup across generations finds exactly what the one-shot finds (the same chunk table, the same plain bytes), but a new generation's blocks hold only the new chunks, so a changed chunk is coded without its previous version in the coder's window, whereas in the one-shot it sits in the same block as its near-identical predecessor; the excess beyond the per-generation metadata is that coder output. - D-60 — 2026-10-13 — **Parallel block encoding (E2-4b): blocks in flight in the reference writer, `--threads` on `lpk a`.** (1) `WriterOptions::encode_threads` (default 1, today's path untouched: every conformance vector and test is unchanged): with N above 1 a closing block is handed to a thread of its own with its `first_chunk`, chunk count and plain length captured, at most N blocks are in flight (the oldest is awaited and written before another is handed over; `finish` drains in order), and every block is written in block order by one write step that does what the sequential path did after the encoder returned — the graph and record checks, priors, the resource envelope, the frame (sealed or plain), the block table, the sequence numbers and the hash chain — so the archive is byte for byte the one the sequential writer produces for the same inputs (tested at the format level with given blocks, dedup, sealing and recovery interleaved, at the tier level with peeled JPEGs and duplicates, and on every class of `small` in release at 1 against 24 threads). (2) A pool-encoded block's graph may not name a record (refused when its encoding completes), so every block in flight is a plain block by construction and the dedup and record rules need only the given blocks' status, recorded at hand-over, and the old generation's blocks — never a block still in flight. - D-61 — 2026-10-16 — **The store path, round 1 of E2-18: no compression context for stored classes, one copy fewer, the frame hash off the feeding thread; G3 judged on `full`.** (1) The class rule of D-47 now decides before any compression context exists: a stored-by-class cluster (video, encrypted-random and the other stored classes) never creates a zstd or LZMA context or a trial in either tier, and a test counts the contexts.
